# Mailing_Service

Проект веб-приложения на Django - сервис управления рассылками, администрирования и
получения статистики.

Приложение позволяет пользователям управлять рассылками сообщений для клиентов. 

В приложении реализована функциональность для создания, просмотра, редактирования 
и удаления рассылок, а также отправка сообщений по требованию и отправка сообщений 
по расписанию.

## Запуск проекта

### Требования
- Python 3.10+
- Django 5.0+

### Установка
1. Подготовка базы данных (`PostgreSQL`):
Перед запуском проекта создайте БД:
```
sudo -u postgres psql -c "CREATE DATABASE your_db_name;"
sudo -u postgres psql -c "CREATE USER your_db_user WITH PASSWORD 'your_db_password';"
sudo -u postgres psql -c "GRANT ALL PRIVILEGES ON DATABASE your_db_name TO your_db_user;"
```
2. Клонировать репозиторий:
```
git clone git@github.com:Nefertitu/Online_store.git
cd Online_store
```
3. Настройка окружения:

Создайте файл .env на основе шаблона (`.env.sample`):
```
cp .env.sample .env
```
Отредактируйте .env (укажите свои секретные ключи, настройки БД и т.д.)

4. Установка зависимостей:
```
poetry install
```
5. Миграции базы данных:
```
python manage.py migrate
```
6. Создание суперпользователя (для доступа в админ-панель):
```
python manage.py csu
```
Следуйте инструкциям в терминале, чтобы задать логин/пароль.
7. Наполнение базы данных группой Менеджеры
```
python manage.py loaddata groups.json

```
7.1. Загрузка данных с указанием формата файла на Windows:
```
python manage.py loaddata groups.json --format json
```
7.2. Наполнение базы данных группой Менеджеры с помощью кастомной команды:
```
python manage.py create_managers
```
8. Локализация и переводы:
- После клонирования проекта скомпилируйте переводы: 
```
django-admin compilemessages
```
9. Запуск сервера:
```
python manage.py runserver
```
10. После запуска сервера откройте в браузере:

[Админ-панель]: http://127.0.0.1:8000/admin/

[Стартовая страница]: http://127.0.0.1:8000/start/

## Приложения и модели

### Модели приложения рассылок (`mailings`):

1. Получатели (`Recipient`):
Основные поля:
* `email` - email получателя (уникальный)
* `fullname` - ФИО получателя (необязательное)
* `owner` - владелец записи (связь с User)
* `comment` - дополнительный комментарий

Особенности:
- Автоматическая фильтрация по владельцу (метод get_recipients_display())
- Строковое представление - email

2. Сообщение (`Message`):
Основные поля:
* `title` - тема письма
* `body` - текст письма
* `owner` - владелец сообщения

Особенности:
- Фильтрация по владельцу (метод get_messages_display())
- Строковое представление - тема письма

3. Рассылка (`Mailing`) - основная модель:
Основные поля:
* `message` - связанное сообщение
* `recipients` - M2M связь с получателями
* `status` - статус (Создана/Запущена/Завершена)
* `start_at`, `end_at` - даты начала и окончания
* `is_periodic` - флаг периодичности
* `period` - период (ежедневно/еженедельно/ежемесячно)
* `next_run` - следующая дата запуска

Основные методы:
* `prepare_for_sending()` - подготовка к отправке (изменение статуса)
* `send_emails()` - непосредственная отправка писем
* `update_status()` - автоматическое обновление статуса
* `schedule_next_run()` - расчет следующего запуска для периодических
* `clean()` - валидация (проверка периода для периодических)

Логика работы:
- Автоматическое обновление статусов при сохранении
- Поддержка периодических рассылок
- Интеграция с почтовым сервисом через send_mail

4. Попытка рассылки (`MailingAttempt`):
Основные поля:
* `mailing` - связанная рассылка
* `status` - статус попытки (Успешно/Не успешно)
* `server_response` - ответ почтового сервера
* `datetime_attempt` - дата и время (автосоздание)

Назначение:
- Логирование результатов отправки
- Хранение ответов почтового сервера
- Анализ проблем с доставкой

Общие особенности:
Все модели:
- Связаны с пользователем/владельцем (owner)
- Имеют методы для красивого отображения
- Поддерживают сортировку (Meta.ordering)

Система рассылок:
- Поддержка разовых и периодических рассылок
- Автоматическое управление статусами
- Логирование всех попыток отправки
- Интеграция со стандартной Django почтой

Безопасность:
- Ограничение доступа к данным по владельцу
- Валидация перед сохранением

### Модель приложения пользователь `user` (`User`):
Назначение:
- Кастомная модель пользователя, заменяющая стандартную модель Django. 
- Использует email в качестве основного идентификатора вместо username.
- Дополнительные поля: телефон, аватар, страна, токен подтверждения
- Флаги: is_manager, is_active

Основные поля:
* `email` (EmailField) - основной идентификатор пользователя (уникальный)
* `phone_number` (PhoneNumberField) - номер телефона с валидацией для РФ
* `avatar` (ImageField) - аватар пользователя (сохраняется в users/avatars/)
* `country` (CharField) - страна пользователя (выбор из предустановленных)
* `token` (CharField) - токен для дополнительной аутентификации
* `is_manager` (BooleanField) - флаг менеджера (расширенные права)
* `is_active` (BooleanField) - флаг активности аккаунта

Особенности:
Аутентификация:
- Замена стандартного username на email (USERNAME_FIELD = "email")
- Поддержка телефонных номеров через phonenumber_field

Права доступа:
- Кастомное разрешение can_block_users для блокировки пользователей
- Метод `can_view_recipients()` проверяет доступ к получателям рассылки
- Флаг `is_manager` предоставляет расширенные права

Дополнительные данные:
- Поддержка аватаров (с автоматическим сохранением)
- Выбор страны из предустановленного списка
- Токен для дополнительных механизмов аутентификации

Методы:
* `str` - отображает email пользователя
* `can_view_recipients(mailing)` - проверяет права доступа к получателям конкретной рассылки

- `MessageDetailView` - просмотр сообщения
- `MessageUpdateView` - редактирование сообщения

3. Работа с рассылками (Mailing):
- `MailingListView` - список рассылок с автоматическим обновлением статусов
- `MailingCreateView` - создание новой рассылки с фильтрацией сообщений/получателей
- `MailingDetailView` - детальная информация + обработка отправки
- `MailingUpdateView` - редактирование рассылки
- `MailingDeleteView` - удаление рассылки

4. Попытки рассылок (MailingAttempt):
- `MailingAttemptListView` - история попыток с пагинацией
- `MailingAttemptDetailView` - детали попытки
- `MailingAttemptDeleteView` - удаление записи о попытке

5. Специальные контроллеры:
- `HomeView` - главная страница со статистикой (отдельные данные для каждого пользователя,

- `StartView` - стартовая страница
- `SearchView` - поиск по всем сущностям

6. Формы (Forms):

- Для создания/редактирования получателей

- Наследует стили из `StyleFormMixin`

* `MessageForm`:
- Для работы с сообщениями
- Автоматическая привязка к владельцу
- Стандартные поля `title` и `body`

* `MailingForm`:
- Основная форма рассылок
- Кастомные queryset'ы для `recipients`(получателей) и `message`(сообщений)
- Специальные виджеты для полей дат
- Поддержка периодических рассылок

* `MailingManagerForm`
- Специальная форма для менеджеров
- Только поле `is_active`
- Для принудительного отключения рассылок

Ключевые особенности:
- Безопасность и права доступа:
- Строгая проверка прав в dispatch-методах
- Разные формы для обычных пользователей и менеджеров
- Фильтрация queryset'ов по владельцу

Бизнес-логика:
- Автоматическое обновление статусов рассылок
- Обработка периодических рассылок
- Интеграция с сервисом статистики

Пользовательский опыт:
- Пагинация списков
- Поиск по всем сущностям
- Информативные сообщения об ошибках/успехе
- Единый стиль форм через `StyleFormMixin`

Производительность:
- Использование кеширования через `DataService`
- Оптимизированные запросы к БД
- Логирование ключевых операций

Все контроллеры наследуют `LoginRequiredMixin` и реализуют:
- Проверку прав доступа
- Кастомные queryset'ы

## Планировщик рассылок (`mailings/scheduler.py`):
Назначение:
Автоматическая система для выполнения периодических email-рассылок по расписанию. Работает в фоновом режиме через APScheduler.

Основные функции:
- Проверка рассылок (check_periodic_mailings()):
- Запускается каждые 5 минут
- Находит активные периодические рассылки (со статусом "Создана" или "Запущена")
- Выполняет отправку писем
- Обновляет статусы и расписание следующих запусков

Управление планировщиком (start_scheduler()):
- Инициализирует фоновый планировщик
- Регистрирует периодическую задачу
- Обеспечивает единственный экземпляр задачи

Особенности работы:
- Интервал проверки: Каждые 5 минут (настраивается в cron-выражении minute="*/5")
- Фильтрация рассылок:
```
is_periodic=True, 
start_at__lte=now, 
end_at__gte=now,
status__in=[Mailing.CREATED, Mailing.LAUNCHED]
```
Защита от дублирования:
- Проверка `_last_run` (не чаще 5 минут)
- Обработка ConflictingIdError
- Гарантия одного экземпляра (`max_instances`=1)

Логирование:
* Записывает в лог:
- Время запуска
- Количество найденных рассылок
- Результаты отправки
- Ошибки выполнения
- Время следующего запуска

Требования:
Установленные пакеты:
* `django-apscheduler`
* `apscheduler`

Пример лога:
```
=== DEBUG TIME: 2023-01-01 12:00:00 ===
Найдено рассылок: 3
Обработка рассылки ID=1, тема: 'Акция января'
Результат: 15/15 отправлено
Следующий запуск задачи: 2023-01-01 12:05:00
Система автоматически запускается при старте Django-приложения и работает в фоновом режиме.
```

## Cервис `UserDataService` приложения `user:
Назначение:
Сервис для кэширования и управления данными пользователей, обеспечивающий оптимизацию запросов к базе данных.

Основные методы:
- `get_users_from_cache(user)`
Получает список пользователей, используя кэширование для оптимизации:

Логика работы:
- Проверяет включено ли кэширование (CACHE_ENABLED)
- Для менеджеров (is_manager=True) возвращает всех пользователей
- Для обычных пользователей возвращает пустой queryset
- Использует ключ кэша `users_list_all`

Особенности реализации:
* Контроль кэширования:
- Проверка глобальной настройки CACHE_ENABLED
- Подробное логирование процесса (для отладки)

* Разграничение доступа:
- Только менеджеры получают полный список пользователей
- Обычные пользователи получают пустой результат

* Технические детали:
- Использует стандартный Django cache framework
- Возвращает QuerySet для совместимости
- Поддерживает аннотации типов (type hints)

Сервис интегрирован в систему views, обеспечивая прозрачное кэширование 
без изменения бизнес-логики.

## Сервисы приложения `mailings`:

1. `StatisticsService`:
Назначение: Сервис для формирования статистических отчетов с учетом прав 
доступа пользователей.

Ключевые методы:
* `get_user_stats(user)` - статистика для обычного пользователя:
- Количество всех попыток рассылок
- Количество успешных попыток
- Общее число получателей
- Общее число сообщений
- Текущая дата/время

*`get_manager_stats()` - расширенная статистика для менеджеров:
- Аналогичные метрики, но по всей системе
- Не требует фильтрации по владельцу

Особенности:
- Использует агрегацию данных напрямую из БД
- Возвращает готовый словарь для использования в шаблонах
- Учитывает временную зону (timezone-aware)

2. `DataService`:
Назначение: Сервис для работы с данными, поддерживающий кэширование и 
оптимизацию запросов.

Основные методы:
* `get_recipients_from_cache(user)`:
- Получает получателей из кэша или БД

Ключи кэширования:
- `recipients_list_all` - для менеджеров
- `recipients_list`_{user_id} - для обычных пользователей
- Оптимизирует запросы через фильтрацию по владельцу

`* get_messages_from_cache(user)`:
- Аналогичная логика для сообщений
- Автоматическая фильтрация по owner
- Поддержка полного списка для менеджеров

* `get_mailings_from_cache(user)`:
Логика для рассылок:
- Оптимизированные запросы с `select_related` и `prefetch_related`
- Поддержка prefetch для связанных получателей
-Автоматическое обновление статусов через _update_mailings_status

Вспомогательный метод:
`_update_mailings_status(mailings)`:
- Пакетное обновление статусов завершенных рассылок
- Использует `bulk_update` для эффективности
- Учитывает временные границы (end_at)

Особенности реализации:
- Гибкая система кэширования с проверкой CACHE_ENABLED
- Детальное логирование операций с кэшем (для отладки)

Поддержка разных уровней доступа:
- Менеджеры видят все данные
- Обычные пользователи - только свои

Оптимизация запросов через:
- `select_related` для `ForeignKey`
- `prefetch_related` для `ManyToMany`
- `only()` для выбора конкретных полей

Примеры использования:

Интеграция:
Сервисы используются в views для:
- Формирования контекста страниц
- Оптимизации запросов к БД
- Предоставления актуальной статистики
- Поддержки кэширования без изменения бизнес-логики
- Система обеспечивает баланс между производительностью и актуальностью данных 
за счет комбинации кэширования и оптимизированных запросов к базе данных.

## Сигналы приложения mailings
1. `check_mailing_completion`:
Триггер: После сохранения рассылки (post_save)

Логика:
- Автоматически проверяет и обновляет статус рассылки через update_status()
- При необходимости сохраняет изменения

Назначение: Контроль актуального статуса рассылок

2. `clear_mailing_cache`
Триггеры:
После сохранения/удаления (`post_save`, `post_delete`) для:
- Рассылок (`Mailing`)
- Получателей (`Recipient`)
- Сообщений (`Message`)

Логика:
- Очищает общие ключи кэша (`mailings_list_all`, `recipients_list_all` и др.)
- Удаляет персональные кэши для всех пользователей (по `user.pk`)

Назначение: Поддержание актуальности кэшированных данных

Особенности:
- Работает с `Redis` через стандартный `Django cache API`
- Подробное логирование операций (вывод в консоль)
- Охватывает все ключевые модели приложения
- Гарантирует согласованность данных после изменений
